# たびのしおり UI/UX 設計

この文書がプロダクト設計の正。実装で迷ったらここに戻る。
決定を変えたら**理由ごと**書き換える。

---

## 0. 設計の芯

> **旅行中に片手で3秒。旅行前に楽しく作れる。**

旅程アプリが失敗する典型は「**入力が仕事になる**」こと。
時刻・カテゴリ・住所・URL を全部埋めさせた瞬間に使われなくなる。
だから本アプリは全編を通じて次の3原則で判断する。

1. **入力は1項目から始まる** — 追加時に必須なのは「場所名」だけ。他は後から足せる
2. **アプリが推測し、人が直す** — カテゴリ・アイコン・リンク種別は自動判定。外れたらタップで直す
3. **ズレることを前提にする** — 旅程は必ず押す。遅延を一発で吸収できることが、正確な時刻入力より価値がある

## 1. 当初案からの変更点と理由

| 当初案 | 変更後 | 理由 |
|---|---|---|
| 画面上部に**1週間カレンダー**、旅行日を色分け | **Day タブ**(Day 1〜N の横スクロール) | 旅行は「3泊4日」であって「週」ではない。週表示は旅行が週をまたぐと分断される(金土日月など)。旅程中の意味単位は曜日ではなく **Day n**。並ぶのが旅行日だけになるので、色分けで区別する必要自体が消える |
| 左に**時刻**(必須の体) | 時刻は**任意**。未入力は「時刻未定」として順序だけ持つ | 「だいたい昼ごはん」を時刻なしで置けないと、計画段階で手が止まる |
| 予定が縦に並ぶだけ | 予定の間に**移動コネクタ**(🚶12分 / 🚃25分) | 旅程アプリの価値の核は「点」ではなく「点と点の間」。次に間に合うかが分かる |
| — | **リフロー**(ここから30分後ろへ) | 旅行中に最も使う操作。1つ遅れたら以降を全部ずらす |
| 地図は Google? Apple? | **どちらか選ぶのではなく、既定を設定で選ばせて外部アプリに投げる** | アプリ内地図SDKは API キー・課金・審査上の追加申告を招く。旅行者は結局ナビを使うので、慣れた地図アプリに渡すのが最短 |
| 食べログなどのリンク | **複数リンク + ラベル自動判定 + 共有シートからの取り込み** | 1件では足りない(公式・食べログ・予約確認)。Safari から「共有」で放り込めるのが最速の入力導線 |

## 2. 情報設計

### 2.1 階層

```
旅一覧
 └ 旅(京都・大阪 3泊4日)
    ├ しおり(リスト)   ← 主画面
    ├ しおり(地図)
    ├ 準備(持ち物・予約・メモ)
    └ 共有(参加者・権限・アクティビティ)
```

**下タブは置かない。** iPhone の縦は貴重で、ヘッダ+セグメント+Dayタブ+タブバーを積むと
本文が半分以下になる。切り替えは以下で足りる。

- リスト ⇄ 地図: ヘッダ直下の**セグメント**
- 準備・共有・設定: ヘッダ右の **⋯ メニュー**

### 2.2 起動時の着地点(重要)

- **進行中の旅がある** → その旅の**今日の Day** を直接開く。旅一覧を経由させない
- 旅行前(開始7日以内) → その旅の Day 1
- どれも該当なし → 旅一覧

旅行中に「アプリを開く → 一覧 → 旅を選ぶ → 今日を探す」を毎回やらせない。

### 3.1 タイムラインの表現

- **左列に時刻、右に縦レール、レール上にカテゴリアイコン**(当初案どおり)
- 所要時間は**レールの長さでは表さない**。長さで表すと 3時間の予定が画面を占領し、
  1日の全体像が見えなくなる。所要時間は `1h30` としてカードに出す
- ただし**2時間以上の空きがある区間だけ**レールを伸ばし、「⌛ 2時間30分の空き」と出す。
  「ここに何か入れられる」が一目で分かるのが計画段階で効く
- **現在時刻ライン**は旅行中の当日のみ。開いた瞬間そこにスクロール

### 3.2 予定カード(閉じた状態)

| 行 | 内容 |
|---|---|
| 1 | **場所名**(太字・1行、溢れは省略) |
| 2 | 補助情報のうち**あるものだけ**: 所要時間 / メモ1行 / 予約バッジ / リンク数 |
| 右端 | **地図ボタンのみ常設** — 旅行中の最頻操作なので1タップで届く位置に置く |

- **タップ** → 詳細シートを開く(下から。中間スナップあり)
- **長押し** → コンテキストメニュー(ここから30分後ろへ / 複製 / 別の Day へ移動 / 削除)
- **左スワイプ** → 削除、**右スワイプ** → 完了チェック(旅行中に「行った」を潰す快感)

### 3.3 移動コネクタ

- 連続する2地点の間に `🚶 8分` `🚃 25分` `🚗 15分` を表示
- 手段は**距離から自動推定**(〜1.2km: 徒歩 / 〜30km: 電車 / それ以上: 車・新幹線)。タップで変更
- **タップすると既定の地図アプリで経路検索**(出発地=前の地点、目的地=次の地点)
- 移動時間 > 次の予定までの空き時間 のとき **⚠️ 間に合わない可能性** を赤字で出す。
  これが「予定を詰め込みすぎた」を計画段階で気づかせる唯一の仕掛け
- **通信が要る精度の高い所要時間は取りに行かない**(API課金・プライバシー申告が増える)。
  直線距離ベースの概算 + 手入力での上書き。概算であることを `約` で明示する

### 3.4 遅延の吸収(リフロー)

旅行中に必ず起きる「押している」への対処。

- 予定を長押し → **「ここから30分後ろへ」**(15/30/60分、任意)
- 以降の**時刻ありの予定すべて**をまとめてずらす。ずらした後に
  **「元に戻す」スナックバー**を数秒出す(誤操作の取り返し)
- 宿のチェックイン時刻など「ずらしたくない」項目は **📌 固定**をつけると対象外になる

## 4. 予定の追加と編集

### 4.1 追加は「名前だけ」

FAB → **1行の入力欄だけが出る**。名前を打って完了。それで予定が1件できる。

- 入力中に**候補サジェスト**を出す(同じ旅の中で既出の地名、よく使う定型:「朝食」「移動」「チェックイン」)
- Enter で**連続追加**(閉じない)。計画段階で行きたい場所を10件まとめて放り込める
- 追加された予定は**その Day の末尾・時刻未定**に入る。あとから並べ替える

### 4.2 カテゴリ・アイコンは自動推定

毎回13個から選ばせるのは苦行。**場所名から辞書マッチで推定**し、外れたときだけ直させる。

```
城 / 天守 / 櫓            → 🏯 城・史跡
寺 / 院 / 大仏 / 神社 / 宮 → ⛩ 寺社
公園 / 庭園 / 展望 / 岬 / 滝 → 🏞 景色・自然
美術館 / 博物館 / 記念館   → 🖼 美術・博物
ラーメン / 食堂 / 寿司 / 焼肉 / レストラン → 🍜 レストラン
カフェ / 珈琲 / COFFEE     → ☕ カフェ
居酒屋 / バー / BAR / 酒場 → 🍶 居酒屋・バー
温泉 / 湯 / スパ / 銭湯    → ♨️ 温泉
ホテル / 旅館 / 宿 / INN   → 🛏 宿
駅 / 空港 / 港 / IC        → 🚉 移動
モール / 商店街 / 市場 / 土産 → 🛍 ショッピング
体験 / 乗船 / クルーズ / 遊園地 → 🎡 アクティビティ
(該当なし)                → 📍 その他
```

- 推定でついたアイコンには**初回だけ小さなヒント**を出す(「タップで変更できます」)
- 手で変えたら**その旅の中では学習**し、同じ語で再推定しない

#### 色は6系統だけにする

13カテゴリに13色を割り当てない。**人が一目で区別できる色数を超える**ため、
色は6つの系統に束ね、系統の中は**絵文字の形**で見分ける。
色だけに頼らないので、色覚特性のある人にも伝わる。

| 系統 | 含むカテゴリ | 色の役割 |
|---|---|---|
| 文化 | 城・史跡 🏯 / 寺社 ⛩ / 美術・博物 🖼 | 藍 |
| 自然 | 景色・自然 🏞 | 緑 |
| 食 | レストラン 🍜 / カフェ ☕ / 居酒屋・バー 🍶 | 橙 |
| 買う・遊ぶ | ショッピング 🛍 / アクティビティ 🎡 | 赤紫 |
| 泊まる・癒す | 宿 🛏 / 温泉 ♨️ | 青緑 |
| 移動・その他 | 移動 🚉 / その他 📍 | 灰 |

### 4.3 詳細シート(段階的開示)

タップで開くボトムシート。**上から使用頻度順**に並べる。

1. 場所名
2. 時刻 / 所要時間(どちらも任意。「時刻を決めない」トグル)
3. カテゴリ
4. **地図** — 場所を検索してピンを確定(緯度経度を保存)。未確定なら名前で検索に飛ぶ
5. **リンク**(複数) — URL を貼ると**ラベルを自動判定**
   - `tabelog.com` → 食べログ / `jalan.net`・`travel.rakuten` → 予約 /
     `instagram.com` → 写真 / それ以外はドメイン名
6. メモ(自由記述)
7. **予約**(予約済トグル / 人数 / 予約番号)— ホテルとレストランで効く
8. 費用(任意。将来の割り勘で使う)

### 4.4 Safari からの取り込み(本命の入力導線)

食べログや公式サイトを見ている最中に「**共有 → たびのしおり**」で
**インボックスに溜まる**。あとで Day にドラッグして配置する。

- iOS の Share Extension が必要(ネイティブ実装。フェーズC以降)
- 取り込み時にページタイトルを場所名、URL をリンクとして自動セット

### 4.5 並べ替え

- **ドラッグ&ドロップ**。ドラッグ中は触覚フィードバック
- 時刻ありの予定を動かしたときの挙動は**初回だけ聞いて記憶**する
  - 「時刻はそのまま(順序だけ入れ替え)」/「移動先に合わせて時刻を調整」
- **Day をまたぐ移動**は、ドラッグして上部の Day タブにホバー → その Day に落ちる

## 5. 地図ビュー

セグメントで切り替える、その Day の全地点を1枚に。

- ピンは**番号付き**(訪問順)+ カテゴリ色
- 順路を線で結ぶ(直線でよい。経路探索はしない)
- ピンタップ → 下部にカードが出る → タップで詳細シート
- 「**この Day 全体を地図アプリで開く**」ボタン

**実装は段階的に。** 地図の埋め込みは API キー・利用規約・プライバシー申告が絡むので、
初期は**外部アプリへのリンクのみ**とし、埋め込み地図はフェーズDで判断する。

### 5.1 外部地図アプリの扱い

**Google と Apple のどちらかに決めない。ユーザーに選ばせる。**
日本では Google Maps 派が多数だが、Apple Maps 派も一定数いる。
初回の地図タップ時に一度だけ聞き、設定でいつでも変更できるようにする。

| 既定 | URL |
|---|---|
| Apple Maps | `http://maps.apple.com/?q=<名前>&ll=<lat>,<lng>` |
| Google Maps アプリ | `comgooglemaps://?q=<名前>&center=<lat>,<lng>` |
| Google Maps Web(アプリ未導入時のフォールバック) | `https://www.google.com/maps/search/?api=1&query=<lat>,<lng>` |
| 経路(コネクタから) | 各アプリの `daddr` / `directionsmode` 相当 |

- **`comgooglemaps` を Info.plist の `LSApplicationQueriesSchemes` に登録**しないと
  `canOpenURL` が常に false を返し、アプリが入っていても Web に落ちる
- 地図ボタン**長押しで「別の地図アプリで開く」**(既定を変えずに一回だけ切り替え)

### 5.2 リンクを開く

アプリ内ブラウザ(`SFSafariViewController` / Capacitor Browser)で開く。
Safari に飛ばしてアプリを離れさせない。

## 6. 共有(サーバーを持たない)

### 6.0 方式:しおりを1ファイルにして送り合う

**同期サーバーを持たない。** 旅程を1ファイルに書き出し、共有シートで送る。
受け取った側は自分の手元とつき合わせて取り込む。

```
  A: しおりを作る → 書き出す ──[LINE / AirDrop / メール]──▶ B: 取り込む
                                                              ↓ 直す
  A: 取り込む ◀──────────────[LINE / AirDrop / メール]──── B: 書き出す
```

**この1点で以下がまとめて解ける。**

| | 同期サーバーあり | この方式 |
|---|---|---|
| プライバシーラベル | 「データを収集しています」 | **「データを収集していません」** |
| 維持費 | 無料枠→いずれ課金 | **永久に0円** |
| オフライン | 状態機械を自前で作る | 定義上つねにオフライン |
| リリース | 同期基盤の実装ぶん遅い | 早い |

「データを収集していません」は**競合が絶対に言えない訴求**。
tabiori も Wanderlog もサーバーを持っているため。

**正直な弱点は1つ、しかし本質的:** 「編集したら送り返す」を人間が忘れる。
誰が最新を持っているか分からなくなる。→ 緩和は §6.4。

> リアルタイム同期は**捨てたのではなく保留**(ROADMAP B-4)。
> 実際に使って「送り返すのが面倒」という不満が本当に出たら復活させる。
> データモデル(項目単位の updatedAt・論理削除・fractional index)は
> どちらにも使えるので、後戻りのコストはほぼない。

### 6.1 参加のしかた:アカウントを作らせない

- 端末ごとに**匿名ID**を発行し、表示名だけ一度聞く(既定は「ゲスト」)
- **メールアドレスもパスワードも要求しない**
- ファイルを受け取った人は、アプリを入れてタップすれば取り込める

> **なぜアカウントを作らせないか:** App Store Review Guideline **5.1.1(v)** は
> 「アカウント作成をさせるアプリは、アプリ内でアカウント削除を提供すること」を要求する。
> アカウントという概念を持たなければ、この要件と退会導線を丸ごと回避できる。
> Sign in with Apple も**入れない**(入れた瞬間に同じ要件が復活する)。

### 6.2 受け渡しの手段

**ファイル共有を主にする。**

- 拡張子 `.tabishiori`(中身は JSON)を共有シートで送る
- LINE で送れる / AirDrop も使える / 容量制限が緩い
- 受け取り側は Info.plist に書類タイプ(UTI)を登録し、タップでアプリが開く
- **⚠️ Capacitor でファイルを受け取る配線は未検証。フェーズCで実機確認する**

URL 方式(`#` の後ろにデータを埋める)は、フラグメントがサーバーに送られないので
「サーバーなし」を保ったままクリックできるリンクになる。ただし LINE で確実に
タップさせるには Universal Links が必要で、`tsukune131.github.io` という名前の
リポジトリを別に作って `.well-known` を置くことになる。**当面やらない。**

### 6.3 取り込みと衝突:ぶつかった日だけ「案」に分ける

最後にやり取りした時点(**baseline**)を持っておき、そこからどちら側が動いたかで決める。

| | 判定 |
|---|---|
| 自分だけ動いた | 自分のまま |
| 相手だけ動いた | 相手を取り込む |
| どちらも動かない | そのまま |
| **両方動いた** | **その日を「案」に分けて両方残す** |

**衝突していないものまで分岐させない。**
「自分が Day1 に足して、相手が Day3 に足した」は衝突ではないので黙って合流させる。
枝分かれするのは本当にぶつかった日だけ。

**案の粒度は Day。** 人が見比べるのは「フィールド」ではなく「その日の過ごし方」。
Day タブに「案2」バッジを出し、タップで切り替えて見比べ、
**「この案を採用」**で本線に戻す。採用するまでは両方残る。

- 両方が**同じ結論**に達していたら(中身が一致)衝突にしない
- 片側だけの**削除**は衝突ではない。そのまま反映する
- すでに案がある日は**それ以上枝を増やさない**(読めなくなるため)
- 旅そのもの(表題・日程)は案に分けず、動いたほうを採る

> **限界(正直に):** これは CRDT ではない。同じ日を3回以上すれ違いながら往復すると、
> 古い側の変更が拾われないことがある。2人〜数人で送り合う前提の割り切り。

### 6.4 「送り返すのを忘れる」への手当て

この方式の唯一にして本質的な弱点。ゼロにはできないので、気づかせる。

- ヘッダに **「未送信の変更 5件」**(`countUnsentChanges` で数える)
- 共有導線を常設し、変更があるときは目立たせる
- 取り込んだ直後に **「相手が変えた3件」** を一覧で見せる(黙って入るのを防ぐ)
- 各予定に**最後に直した人と時刻**を持たせ、詳細シートで見られるようにする

### 6.5 権限について

サーバーが無いので、**権限は強制できない**(ファイルを渡した相手は何でもできる)。
「閲覧のみ」を作るなら、それは相手のアプリ側の設定にすぎず、
セキュリティ機能ではない ── **そう見えるUIを作らない**。

将来リアルタイム同期に移す場合にのみ、実効のある権限を導入する。

### 6.6 通知

サーバーが無いのでプッシュ通知は飛ばせない。**ローカル通知だけ。**

- 旅行当日、次の予定の**開始15分前リマインド**(これは価値が高い)
- 「相手が変更した」の通知は**構造上できない**。取り込み時にまとめて見せる

## 7. しおり以外の画面

### 7.1 準備(⋯ メニュー)

- **持ち物リスト** — チェックボックス。旅の種類(国内/海外/温泉)でテンプレを提示
- **予約まとめ** — 予約バッジが付いた予定を横断で一覧(空港で「予約番号どこ」を探さない)
- **旅のメモ** — 全体に関わる自由記述

### 7.2 費用(将来)

共有機能があるなら割り勘は相性が良い。ただし**フェーズを分ける**。
予定に「費用」欄だけ先に持たせ、集計は後から乗せる。

## 8. ビジュアル

- **比喩は「紙のしおり」。** 生成りの紙色を基調に、カテゴリ色を差し色として置く
- 配色は `prefers-color-scheme` で OS 追従(ダークモードを別実装しない)
- 角丸は控えめ、影は薄く。**主役は文字情報**であって装飾ではない
- **Dynamic Type 対応**(相対単位で組む)。旅先で親世代が見る場面がある
- タップ領域は最低 **44×44pt**
- 触覚: 並べ替え確定 / チェック / リフロー実行の3箇所のみ(乱発しない)

---

## 9. 広告の置きかた

収益は広告だが、**旅程の可読性を壊した瞬間にアプリの価値が消える**。

- **タイムラインの途中に挿し込まない。** リスト内広告は誤タップを誘い、
  Review Guideline 4.2(最低限の機能)/ 3.2.2 の指摘対象になりやすい
- **画面下端の固定バナー**1枠のみ。セーフエリアを尊重し、FAB と重ねない
- **出さない画面**: 地図ビュー、編集シート、旅行当日の「次の予定」表示
- コンテンツを覆う全画面インタースティシャルは**入れない**

## 11. やらないと決めたこと

| やらないこと | 理由 |
|---|---|
| 週カレンダー表示 | 旅程の単位は「週」ではなく「Day n」。週をまたぐ旅行で分断される |
| 経路探索API による正確な所要時間 | 課金とプライバシー申告が増える。概算 + 手入力で用は足りる |
| アプリ内の地図SDK(初期) | API キー・規約・申告のコスト。外部アプリに投げるほうが旅行者の慣れにも合う |
| アカウント登録 / Sign in with Apple | 5.1.1(v) のアカウント削除要件と退会導線を丸ごと回避するため |
| 同期サーバー(当面) | 非同期のファイル共有で足りる。持たなければ「データを収集していません」を守れる |
| 衝突していない変更まで案に分けること | 枝が増え続けて読めなくなる。分けるのは本当にぶつかった日だけ |
| 実効のない「閲覧のみ」権限 | サーバーが無い以上、渡した相手は何でもできる。守れる顔をしたUIを作らない |
| 旅程内容を広告SDKに渡すこと | 「広告は出すが、あなたの記録は渡さない」を製品の線引きとする |
| 全画面インタースティシャル広告 | 旅行中に開いた瞬間に出ると即アンインストールされる |
| 所要時間をレールの長さで表現 | 長い予定が画面を占領し、1日の全体像が見えなくなる |
