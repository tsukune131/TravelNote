決定日: 2026-08-08。**広告は入れない。自動更新サブスクのみ。**

---

## 1. 決めたこと

| | |
|---|---|
| 収益モデル | **自動更新サブスクリプションのみ**(広告なし・買い切りなし) |
| 月額 | **¥500** |
| 年額 | **未決定(併売を強く推奨。§5)** |
| サブスクリプショングループ | `travelnote_pro` |
| 製品ID(月額) | `com.tsukune.travelnote.pro.monthly` |

### 広告を入れないことで守られるもの

**プライバシーラベルは「データを収集していません」。**
App内課金の決済は Apple が扱い、開発者は購入情報を受け取らない。
同期サーバーも持たない。**開発者の管理下へ移るデータが存在しない。**

これは tabiori も Wanderlog も構造上言えない訴求で、この市場での最大の差別化資産。
**広告SDKを1つ入れた瞬間に失う。二度と検討しない。**

---

## 2. 無料でできること

**無料のままで、アプリの価値がひととおり分かること。**
「課金しないと何もできない」は Guideline 3.1.2 / 4.2 のリジェクト定番であり、
そもそも誰も試せないので広まらない。

- **旅を1つ**持てる(計画中でも旅行中でも)
- その旅では**機能の制限がない**:
  - Day タブ / タイムライン / 時刻の任意化
  - 移動コネクタ / 間に合わない警告 / **リフロー**
  - カテゴリ自動推定 / 外部地図リンク / 複数リンク
  - **共有(書き出し・取り込み・案の比較と採用)**
- 過去の旅は**読み取り専用で残る**(消さない・隠さない)

> **共有は絶対に有料にしない。** 共有はこのアプリの核であり、
> 送られた相手が読めなければ機能そのものが成立しない。

---

## 3. Pro でできること

サブスクは **「継続的な価値(ongoing value)」が Guideline 3.1.2 の要件**。
一度きりで終わる機能を並べると「継続する価値がない」で弾かれる。
だから Pro の軸は**「旅を重ねるほど効く」もの**にする。

- **旅をいくつでも同時に持てる** ← これが主軸。
  次の旅を計画しながら、今の旅を使える
- **過去の旅を編集・複製できる**(「去年の京都をベースに今年のを作る」)
- 写真の添付
- 持ち物テンプレートと、費用の割り勘
- PDF / 印刷での書き出し

### 審査メモに書く「継続的な価値」の説明

```
旅を何本でも同時に計画でき、過去の旅を編集・複製して次の旅に使えます。
旅行のたびに継続してご利用いただく前提の機能です。
```

## 4. 解約したときの扱い(ここが方針の要)

**解約してもデータをロックしない。**

- 作った旅は解約後も**すべて読める**。共有(書き出し)もできる
- できなくなるのは**「2つめ以降の旅を新しく作ること」**と、Pro 専用機能の利用だけ
- 既存の旅の**編集も続けられる**(旅行中に期限が切れて詰むのを避ける)

理由:

1. **データを人質に取るのは「データを収集していません」の思想と矛盾する。**
   端末の中のあなたのものを、支払いで開け閉めしない
2. レビューが荒れる。旅行アプリで旅行中にロックされたら致命的
3. 結果として **「旅行のたびに1か月だけ入る」を許容する設計**になる。
   継続率は下がるが、それは誠実さの対価として受け入れる。
   年に2回旅行する人からは年2回入る

## 5. 月額単独の弱点と、年額の推奨

**旅行は年に1〜3回。月額単独だと、旅行が終わった翌月に解約される。**
これは構造的なもので、機能では埋められない。

競合の tabiori は **¥480/月 と ¥3,900/年** を併売している(年額は月額の約8.1か月ぶん)。
おそらく年額が実質の主力。

### 推奨

| | 価格 | 位置づけ |
|---|---|---|
| 月額 | **¥500** | 「今回の旅行のあいだだけ」。解約前提でよい |
| 年額 | **¥3,000**(月あたり¥250) | 年2回以上旅行する人の本命。tabiori の ¥3,900 より明確に安い |

年額を出すと、月額の解約が「失敗」ではなく**年額への入口**になる。

### 無料トライアル

**14日間**を推奨(StoreKit の introductory offer)。
7日だと短い ── 旅程づくりは数週間かけて少しずつ進むもので、
7日では「旅を2つ持てる」価値を体験しきれない。

> 月額¥500 は決定済み。**年額と無料トライアルは未決定**(D-0 で確定させる)。

## 6. 審査の要件(自動更新サブスク)

Guideline **3.1.2**。ここを外すと確実に差し戻される。

### アプリ内(バイナリ)に必ず入れるもの

- [ ] サブスクリプションの**名称**
- [ ] **期間**(1か月 / 1年)
- [ ] **価格**、および必要なら単位あたりの価格
- [ ] **プライバシーポリシー**への機能するリンク
- [ ] **利用規約(EULA)**への機能するリンク
- [ ] **「購入を復元」ボタン**(設定 または 購入画面に、明示的なラベルで)

### App Store Connect のメタデータ

- [ ] プライバシーポリシーURL(GitHub Pages のものを設定)
- [ ] 利用規約(EULA)を、説明文またはEULA欄に記載

### そのほか

- [ ] **継続的な価値**があること(§3 の説明を審査メモに書く)
- [ ] 期間は最低7日
- [ ] **ユーザーの全デバイスで利用できること**
      → StoreKit 2 の `currentEntitlements` を見れば自動的に満たせる
- [ ] 未購入の端末で購入シートのスクリーンショットを撮る(**プロモコード配布前に**)

## 7. 実装方針

- **`@capgo/native-purchases`(StoreKit 2 直叩き)。RevenueCat は使わない。**
  第三者SDKを1つ入れるたびに「データを収集していません」の申告が揺らぐため
- 購入状態の判定は**端末側で完結**する(`currentEntitlements`)。
  サーバー不要 ── 「サーバーを持たない」方針とそのまま両立する
- **プラグインは静的 import**(動的importで実機が固まった前例あり)
- システムのサブスク管理画面へは `manageSubscriptions()` で飛ばす
- **有料App契約(Paid Applications Agreement)は反映に数日かかる。**
  税務・銀行情報の登録も要るので、フェーズDの最初に着手する

### 実装前に確かめること

- [ ] Sandbox でのサブスク購入・更新・解約の挙動(**実機が要る。C-5 と同時に**)
- [ ] 期限切れの検出と、その後も既存の旅が編集できること
- [ ] 「購入を復元」が別端末で効くこと

---

## 8. やらないと決めたこと

| やらないこと | 理由 |
|---|---|
| 広告 | 「データを収集していません」を失う。最大の訴求と引き換えにする価値がない |
| 買い切り | 一度きりでは維持できない。旅行は繰り返し発生するので継続課金と相性がある |
| RevenueCat | SDKを増やすとプライバシーの申告が揺らぐ。StoreKit 2 を直接叩く |
| 共有機能の有料化 | 送られた相手が読めなければ、機能そのものが成立しない |
| 解約時のデータロック | 端末の中のユーザーのものを、支払いで開け閉めしない |
| 消耗型・従量課金 | 旅程アプリに合わない |
